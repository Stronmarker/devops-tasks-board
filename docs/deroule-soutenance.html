Ce que je dis, ce que je montre

Douze minutes de présentation, dont cinq de démonstration. Le texte est écrit pour être dit, pas lu. Les repères de gauche donnent le temps écoulé et la diapositive en cours.

Avant d'entrer dans la salle

À préparer une heure avant

  1. Réveiller Render. Le plan gratuit endort le service après 15 minutes. Ouvrez l'application dans le navigateur et attendez qu'elle réponde, sinon le premier chargement devant le jury prendra 50 secondes.
  2. Démarrer le cluster. make k8s-start puis make k8s-status pour vérifier les 4 pods.
  3. Ouvrir quatre onglets : l'application Render, GitHub Actions, le dépôt GitLab, et l'application du cluster sur localhost:30080.
  4. Préparer deux terminaux côte à côte, police agrandie, dans le dossier du projet.
  5. Faire la démo une fois en entier, seul. Toutes les commandes de ce document doivent avoir été tapées au moins une fois aujourd'hui.

Présentation

0:00Diapo 1

Bonjour. Je vais vous présenter le DevOps Tasks Board, une application de gestion de tâches en équipe. Ce n'est pas l'application qui est intéressante, elle est volontairement simple. Ce qui est intéressant, c'est le chemin qu'elle parcourt : de mon poste de développement jusqu'à une production accessible en ligne, en passant par la conteneurisation, l'orchestration et l'intégration continue.

Je terminerai par une démonstration en direct, et par trois pannes que j'ai réellement rencontrées.

0:45Diapo 2

L'architecture est en trois tiers. Une interface React, une API Express, une base PostgreSQL. La règle est simple : chaque étage ne parle qu'à son voisin. Le navigateur n'atteint jamais la base. Seule l'API y accède, et elle est la seule à détenir les identifiants de connexion.

Un point auquel je tiens : le schéma de la base est défini dans un seul fichier SQL. Ce même fichier initialise la base en local, dans le cluster Kubernetes et en production. Quand je modifie le schéma, je le modifie une fois.

1:45Diapo 3

Le même code source s'exécute de trois façons, pour trois usages différents.

En local, Docker Compose, avec le code monté depuis mon disque : je modifie un fichier, il est actif dans la seconde. Dans le cluster Kubernetes, le code est figé dans une image, et c'est là que je démontre l'orchestration. En production, Render, qui construit son propre artefact à partir de mon dépôt.

Je veux souligner une limite tout de suite, avant qu'on me la trouve. Render n'utilise ni mes Dockerfiles ni mes manifests Kubernetes. L'image que mon pipeline teste n'est donc pas exactement celle qui tourne en production. Une chaîne mature publierait l'image sur un registre et déploierait celle-là partout. C'est ce que je ferais avec plus de temps.

Effet recherché Annoncer soi-même la faiblesse désarme la question. Un jury qui découvre une limite que vous aviez identifiée vous fait confiance sur le reste.
3:00Diapo 4

Le pipeline se déclenche à chaque push. Six étages, et aucun ne démarre si le précédent a échoué. Une régression ne peut donc pas atteindre la production.

D'abord l'analyse statique du code sur les deux paquets. Ensuite les tests du backend, 48 au total, dont des tests d'intégration qui tournent contre un vrai PostgreSQL démarré à côté du job. Puis les tests du frontend, 18, qui montent réellement les composants dans un DOM. Ensuite la construction des deux images Docker. Puis le déploiement, uniquement depuis la branche principale.

Le dernier étage est celui auquel je tiens le plus. Il ne dit pas « déployé », il dit « qui répond ». Il interroge la route de santé sur l'URL publique jusqu'à obtenir une réponse saine. Et comme cette route exécute une vraie requête SQL, un déploiement n'est validé que si l'application et sa base répondent toutes les deux.

4:15Diapo 5

L'authentification fonctionne par équipe. Une équipe est un espace fermé. On y entre de deux façons : soit on la crée, et on en devient chef, soit on présente le code à six chiffres que le chef a remis.

La session repose sur deux jetons. Un jeton d'accès qui vit quinze minutes et ne quitte jamais la mémoire du navigateur. Et un jeton de rafraîchissement qui dure sept jours, stocké en base côté serveur. C'est cette présence en base qui rend la déconnexion réelle : je supprime la ligne, l'accès est coupé.

Chaque rafraîchissement consomme le jeton présenté et en émet un nouveau. Un jeton ne sert donc jamais deux fois. Et si un jeton déjà consommé revient, c'est qu'une copie circule. Impossible de savoir si c'est le voleur ou la victime qui l'envoie, alors je révoque toute la session.

5:45Diapo 6

Voici les menaces que j'ai identifiées et ce que j'ai fait pour chacune.

La plus intéressante est le code d'équipe. Six chiffres, c'est un million de combinaisons. Un script les épuise en quelques minutes. Le principe est bon, il est utilisé par Slack ou Discord, mais la version brute est faible. J'ai donc limité à cinq tentatives par quart d'heure, rendu le code renouvelable par le chef, et fait en sorte que l'API ne le transmette jamais à un simple membre.

Il reste un risque que je n'ai pas traité, et c'est un choix, pas un oubli. Le jeton de rafraîchissement est dans le stockage du navigateur, donc lisible par un script injecté. Un cookie sécurisé y résisterait, mais mes deux services sont sur des domaines différents, ce qui rendrait la configuration nettement plus fragile. J'ai préféré une chose qui marche de façon fiable, avec le risque documenté.

7:00Diapo 7

Sur Kubernetes, je veux être franc : pour une application de cette taille, ce n'est pas indispensable. Docker Compose suffirait.

Mais Kubernetes a eu un effet concret sur mon code. Le backend tourne en deux exemplaires. Deux pods ne partagent pas leur mémoire. Une session stockée côté serveur serait donc invisible d'un pod à l'autre, et je serais déconnecté une fois sur deux, au hasard. C'est cette contrainte d'infrastructure qui m'a imposé une authentification sans état.

Je ne l'ai pas décidé en lisant un article. Je l'ai déduit de mon fichier de déploiement. Et je vais vous le montrer.

Effet recherché C'est le meilleur argument de la soutenance. Il prouve que vous avez compris le lien entre l'infrastructure et le code, et non recopié des fichiers de configuration.
8:00Diapo 8

Un mot sur la base. Le plan gratuit de Render supprime la base au bout de trente jours. J'ai donc outillé la reprise : un script rejoue le schéma sur n'importe quelle base, et il est idempotent, donc rejouable sans risque sur une base déjà remplie.

Ce script n'est pas théorique. C'est lui qui a migré ma base de production quand j'ai ajouté l'authentification, sans interruption et sans perte de données.

Et parce que ces commandes peuvent atteindre la production, la plus destructive exige de taper le mot « supprimer » en toutes lettres, et refuse de s'exécuter sans clavier. Aucun pipeline ne peut la déclencher.

9:00Diapo 9

Trois pannes m'ont appris plus que le reste du projet.

La première, une page blanche en production. Le serveur renvoyait 200, le HTML, le CSS et le JavaScript arrivaient correctement. Mais le bundle plantait au démarrage. J'ai perdu du temps parce que je vérifiais avec curl, qui n'exécute jamais le JavaScript. La leçon : un code 200 sur une application monopage ne prouve rien.

La deuxième, un service qui redémarrait en boucle. Une variable d'environnement avait été mise dans un groupe non rattaché au service. Ce qui m'a sauvé, c'est que ma route de santé teste vraiment la base : elle m'a dit « base indisponible » au lieu de « erreur 500 ».

La troisième est la plus instructive. Impossible de créer une équipe. Le backend était correct, les tests passaient, la sécurité était bonne. Mais quatre erreurs différentes renvoyaient le même message, et la règle du mot de passe n'était écrite nulle part. L'application était irréprochable techniquement et inutilisable.

Le point commun des trois : ce que je vérifiais n'était pas ce qui comptait. Chacune a produit un test qui l'aurait attrapée.

Questions probables

Kubernetes était-il nécessaire ici ?

Non, et je l'assume. Pour une application de cette taille, Docker Compose suffirait, et Render n'utilise même pas mes manifests. Sa valeur ici est double : c'est une compétence demandée par le sujet, et surtout, la contrainte des deux répliques a réellement déterminé mon choix d'authentification. L'exercice a eu un effet concret sur mon code.

Pourquoi un jeton plutôt qu'une session côté serveur ?

Trois raisons, toutes liées à mon déploiement. Mes deux pods ne partagent pas leur mémoire. Render éteint le service après quinze minutes d'inactivité, donc toute session en mémoire mourrait au redémarrage. Et mon frontend et mon API sont sur deux domaines différents, ce qui complique beaucoup les cookies.

Le prix à payer, c'est qu'un jeton d'accès ne se révoque pas avant son expiration. C'est pour ça qu'il ne dure que quinze minutes, et que la révocation passe par le jeton de rafraîchissement, lui stocké en base.

Le jeton dans le navigateur, ce n'est pas dangereux ?

Si, c'est le risque résiduel que j'ai identifié. Un script injecté pourrait lire le jeton de rafraîchissement. J'ai réduit la surface : le jeton d'accès, lui, ne touche jamais le disque. Un cookie sécurisé serait meilleur, mais entre deux domaines Render il impose une configuration que je jugeais trop fragile pour le temps dont je disposais.

Pourquoi make et pas les scripts demandés dans le sujet ?

Un Makefile donne une entrée unique et documentée pour toutes les opérations, avec make help qui les liste. Il gère les dépendances entre cibles, ce qu'un script shell ne fait pas : k8s-start déclenche la construction des images et la génération de la configuration avant d'appliquer les manifests.

Le comportement demandé est là, sous une forme que je considère plus maintenable. Le choix est justifié par écrit dans le dépôt.

Comment gérez-vous les secrets ?

Différemment selon l'environnement. En local, dans le fichier Compose, avec des valeurs de développement assumées comme publiques. Dans le cluster, un Secret Kubernetes. En production, les variables d'environnement de la plateforme.

Un point important : un Secret Kubernetes n'est pas chiffré, il est seulement encodé en base64. Pour de la vraie production j'utiliserais Sealed Secrets, SOPS ou un coffre externe comme Vault. C'est écrit en commentaire dans le manifest.

Et le backend refuse de démarrer si la clé de signature est absente, plutôt que d'utiliser une valeur par défaut qui serait dans le dépôt, donc connue de tous.

Que testent réellement vos tests ?

Trois niveaux. Des tests unitaires sur les briques de sécurité : hachage, salage, falsification de jeton. Des tests d'intégration qui démarrent un vrai serveur HTTP contre une vraie base, et qui vérifient notamment qu'une équipe ne voit jamais les données d'une autre. Et des tests de composants qui montent l'interface dans un DOM.

Ce dernier niveau vient directement de la panne de page blanche. C'est le seul type de test qui l'aurait détectée.

Que se passe-t-il si votre base de production disparaît ?

Je crée une nouvelle base, je mets à jour la variable de connexion du service, et je lance une commande qui rejoue le schéma et les données. Quatre étapes documentées dans le README. La procédure a déjà servi pour une migration réelle.

Pourquoi Docker Desktop plutôt que Minikube ?

Docker Desktop était déjà installé et intègre un cluster Kubernetes complet. Cela évitait un second hyperviseur et un second démon Docker sur la machine. Les objets manipulés sont exactement les mêmes : Deployments, Services, ConfigMaps, Secrets, sondes. Les manifests fonctionneraient sur Minikube sans modification.

La règle qui compte

Si une démonstration échoue, ne la relancez pas trois fois. Dites ce qui devait se passer, expliquez pourquoi vous pensez que ça a échoué, et passez à la suite. Un jury retient la capacité à diagnostiquer, pas la perfection de la démonstration.
