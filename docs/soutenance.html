05  Authentification

Une équipe, un code, deux jetons

Une équipe est un espace fermé. On y entre de deux façons : en la créant, et on en devient alors chef, ou avec le code à 6 chiffres remis par le chef.

Jeton d'accès

15 MINUTES · EN MÉMOIRE

Accompagne chaque requête. Ne touche jamais le disque et disparaît à la fermeture de l'onglet.

Jeton de rafraîchissement

7 JOURS · STOCKÉ EN BASE

Sert uniquement à obtenir une nouvelle paire. Sa présence en base rend la déconnexion réelle.

1. connexion → accès + rafraîchissement 2. rafraîchissement → nouvelle paire, l'ancienne est consommée 3. rejeu de l'ancien → session compromise, reconnexion requise 4. jeton légitime → révoqué lui aussi 5. en base → 0 actif, 2 révoqués
Pourquoi couper la session légitime aussi ? Quand un jeton déjà consommé revient, impossible de savoir si c'est le voleur ou la victime qui l'envoie. On révoque tout et on redemande une connexion. La fenêtre d'exploitation passe de 8 heures à 15 minutes.

La sonde détecte plus qu'un crash. Elle exécute un SELECT 1 : un backend vivant mais incapable de joindre la base est redémarré, ce que Docker Compose ne sait pas faire. Le seuil est fixé à 6 échecs pour qu'une base momentanément indisponible ne déclenche pas une boucle de redémarrages.

08  Données

Un plan de reprise, pas une intention

La base managée est supprimée au bout de 30 jours sur le plan gratuit. La procédure de reprise est outillée et a déjà servi.

CommandeCibleEffetProtection
make db-reset Locale, toujours Vide et recharge les données de démonstration passe par Docker Compose
make db-bootstrap Désignée par l'URL Crée ce qui manque, laisse le reste intact idempotent
make db-suppr Désignée par l'URL Supprime les tables elles-mêmes « supprimer » à taper, refus sans clavier
Le script de restauration n'est pas théorique. C'est lui qui a migré la base de production lors de l'ajout de l'authentification, sans interruption ni perte de données parce que le fichier SQL est écrit pour s'appliquer aussi bien à une base vierge qu'à une base déjà peuplée.

09  Retour d'expérience

Trois pannes, trois leçons

Page blanche

Le serveur répondait 200

HTML, CSS, JavaScript : tout arrivait correctement. Mais le bundle plantait au démarrage, faute d'un plugin jamais branché dans la configuration de build.

Leçon : un 200 sur une application monopage ne prouve rien. curl n'exécute jamais le JavaScript.

503 en boucle

Une variable jamais déclarée

Le service redémarrait sans fin en production. Les variables avaient été mises dans un groupe non rattaché au service.

Leçon : une sonde qui teste vraiment la base transforme une panne opaque en diagnostic de 30 secondes.

Formulaire bloqué

Un message pour quatre causes

Impossible de créer une équipe. Quatre erreurs distinctes renvoyaient le même texte, et la règle du mot de passe n'était écrite nulle part.

Leçon : le backend était correct, les tests passaient, la sécurité était bonne. L'application était quand même inutilisable.

Les trois ont un point commun : ce qui était vérifié n'était pas ce qui comptait. Chacune a produit un test qui l'aurait attrapée.
